# Domain model

24 tables. Every table is created by Alembic; `alembic check` passes with no
drift against the models.

---

## 1. Tenancy

`organisation` is the tenant. `user` and `organisation` are many-to-many
through `user_organisation`, which carries the **role** — a user's role is a
property of the pairing, not of the user.

Every tenant-owned table carries `organisation_id` explicitly, including
`story`, which could otherwise only be scoped by joining through evidence.

`question.organisation_id` is nullable, because a publicly submitted question
belongs to nobody until it is triaged.

## 2. The evidence spine

```
source ──▶ evidence ──▶ story
             │  │
             │  └──▶ indicator (current value)
             ▼
          project ──▶ programme
```

**`source`** — where a claim came from. Typed (`official_document`,
`field_report`, `interview`, …), with a transparent verification state and a
reliability classification that carries a written rationale rather than an
unexplained score.

`VerificationState` has **no "true" value**, by design: `unverified`,
`in_review`, `verified`, `disputed`, `rejected`. Spec section 11 forbids
automatically labelling a source true, so the states describe how far review
got and what it found, never that the content is fact.

**`evidence`** — a claim, with its source, date, owner and verification state.

Its `reference` is a permanent, human-readable identifier —
`EV-2026-000001` — generated by the **database** at insert from a sequence, so
it is assigned exactly once and cannot drift. An evidence record must stay
citable by the same reference for its whole life.

`version` rises on every content edit, and the approval trail stores the
version each decision covered.

**`indicator`** — the definition, baseline and target of a measure.
`evidence.measured_value` is an observation of it at a point in time. An
indicator's `current_value` is never typed in by hand: it is whatever the most
recent approved evidence measured.

**`story`** — public information built from evidence. Carries its own
`organisation_id` and a `StoryStatus` through the editorial lifecycle.

## 3. Geography

`geographic_area` is a self-referential tree:

```
country → region → state → lga → ward → community
```

**The table is `geographic_area`, not `geography`.** PostGIS already defines a
type called `geography`, and a table of that name collides with it — `CREATE
TABLE geography` fails outright. The model class is still `Geography`; only the
table name differs, and there is a comment on it saying not to "fix" this.

A parent must sit **strictly above** its child in the level order. Levels may
be skipped, because not every country has every tier, but a node can never be
placed under something at or below its own level — that would make roll-ups
meaningless and could create a cycle.

Descendants are resolved with a recursive CTE, so "everything in this state"
does not require the caller to know how deep the tree goes.

## 4. The approval trail

`approval_record` is addressed by `(entity_type, entity_id)` rather than by a
foreign key per kind, so evidence, stories, questions and integrity findings
share one trail. See `docs/APPROVAL_WORKFLOW.md`.

## 4a. Information integrity

**`integrity_signal`** — a claim circulating in public, and what was found out
about it. `finding` is the conclusion; `assessment` is the reasoning behind it,
and they are separate columns because a verdict with no reasoning is the
unexplainable intelligence spec section 4 rules out.

The table has **no column for who spread a claim** — no account, handle,
audience or segment. The prohibition is enforced by there being nowhere to put
such a thing rather than by remembering not to, and a test asserts it. `source`
and `circulation` describe a channel. See `docs/INFORMATION_INTEGRITY.md`.

## 4b. Readiness

```
scenario ──▶ playbook_step
   │
   └──▶ drill ──▶ drill_finding
```

**`scenario`** — something the organisation must be ready for. Its `status` is
**declared**, with a rationale and a declaring user, and checked against a
floor computed from the other three tables. `last_drill_date` is derived from
completed drills rather than typed in, so the date and the account of what
happened cannot disagree.

**`playbook_step`** — one step of the plan. `responsible_role` is not nullable:
a plan that does not say who acts is not a plan. Positions are unique per
scenario and must form 1..n.

**`drill`** — a rehearsal. Cancelled drills are kept with their reason, because
the history of what was *not* rehearsed is part of what a readiness record is
for.

**`drill_finding`** — what a rehearsal showed to be wrong. Confirmed resolved
by a different person from the one who raised it. Like `integrity_signal`, it
has **no blame column**, and a test asserts that. See `docs/READINESS.md`.

## 5. Audit

`audit_log` records every state transition: actor, action, entity, old values,
new values, address, user agent. Action names are stable identifiers, not
prose, because they are queried and reported on.

## 6. Tables that exist but are not yet used

Honesty about the schema, per spec section 81:

- **`location`** — a PostGIS point, linked to projects and evidence, but no
  endpoint manages it.

## 7. Conventions

**Enums persist values, not member names.** `values_callable=_enum_values`
makes SQLAlchemy store `"super_admin"` rather than `"SUPER_ADMIN"`, so the
database and the wire format are identical. Without it every API payload would
disagree with every stored row.

**Constraint naming convention** is set on the metadata. Without it, Alembic
emits `drop_constraint(None, ...)` for Postgres-assigned names, which cannot
run.

**`TimestampedModel`** gives every table `id`, `created_at`, `updated_at`,
`created_by`, `updated_by`.

## 8. Things Alembic autogenerate cannot be trusted with

Recorded because each one was a real failure:

| Thing | Why | Handled by |
|---|---|---|
| Sequences | Never emitted at all | Explicit `CREATE SEQUENCE` in the baseline |
| Extensions | Never emitted | Explicit `CREATE EXTENSION` for postgis and pg_trgm |
| Native enum types on downgrade | Table dropped, type left behind, next upgrade fails with "type already exists" | Explicit `DROP TYPE IF EXISTS` list |
| `spatial_ref_sys` | PostGIS's own table looks like drift, and autogenerate proposes dropping it | `geoalchemy2.alembic_helpers` in `env.py` |
| varchar → enum | Emits `alter_column` alone: the type does not exist yet and Postgres will not cast without `USING` | Hand-written `CREATE TYPE` + `USING` cast |

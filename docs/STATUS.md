# EPIRO — Build Status

**Last updated:** 2026-09-19 · **Branch:** `claude/beautiful-fermi-npx5r9`

This document exists because spec section 81 forbids presenting a planned
feature as one that already works. Every claim below carries a label:

| Label | Meaning |
|---|---|

| **PARTIAL** | Built for some cases; the gaps are named explicitly. |

### Front end

**PARTIAL.**

**CONFIRMED:** the public portal (nine routes, including published corrections)
and the staff workspace — sign-in, plus evidence, story and question screens,
and the intelligence dashboard with its drill-downs. Each record page offers
exactly the workflow actions that person's role and that record's state allow,
and says what the record is waiting for when they can do nothing.

Verified against a running stack by driving all three workflows end to end as
four different people, including every separation of duties: a verifier
refused when approving their own verification, a responder refused when
approving their own answer, and an approver refused when publishing what they
approved.

The dashboard was verified the same way, against a database seeded so that
suppression actually fires: every headline figure and every bucket in all six
measure sections was read off the rendered page, each link followed, and every
drill-down total agreed with the number that led to it. The same check was run
again with filters applied — by area, by verification state, by theme — and 37
filtered figures all reconciled. A withheld bucket, a
withheld headline figure, a `(not recorded)` bucket resolving through an IS
NULL basis, a bucket showing an area name while linking by its identifier, and
a refused measure were each looked at on screen rather than assumed from the
tests.

The session token is held in an httpOnly cookie, so page script cannot read
it and every authenticated call happens on the server.

**NOT BUILT:** creating evidence or drafting a story in the interface (both
exist in the API), the readiness matrix as a screen (API-only, and deliberately not public at all),
field missions as a screen, project and programme management, and user
administration. The dashboard's drill-downs inherit those gaps: a row for a
mission, a signal, a scenario or a project is listed without a link, and the
page says so rather than offering one that would 404.

## Things that are deliberately absent

Spec section 4 forbids these, and none of them exist anywhere in the codebase.
This list is here so that a later contributor understands the absence is a
decision, not an oversight:

- Voter profiling, political preference inference, political susceptibility
  scoring.
- Demographic political targeting or microtargeted political messaging.
- Covert influence operations or automated political persuasion.
- Psychological profiling for political purposes.
- Anything that would treat a citizen as a target rather than as someone the
  platform is accountable to.

Section 20's limit on collection is enforced in code: an anonymous question
cannot carry a contact address, and the audit entry for a public submission
records neither the submitter nor the text of what they asked.

The information integrity feature (§25–26) is where these prohibitions are
easiest to break, because the obvious next feature is always "who is spreading
this". The `integrity_signal` table therefore has **no column** for an account,
a handle, an audience, a segment or a person, and a test asserts that none has
appeared. The public wording is held to the same line by a test that no
finding's description says "spread by", "targeted" or "audience". The record is
about information; the people carrying it are not the platform's business.

The same applies inward. A readiness drill (§28–31) is the obvious place a
"who let us down" column would appear, so `drill_finding` has none, and a test
asserts that. A finding describes what the response could not do. Section 4's
prohibition on profiling is not only about citizens.

Intelligence (§21–22) is the third place it could have gone wrong, because
"intelligence" is the word that invites profiling. It is defined here as
counting the platform's own records and nothing else: the dimensions are a
closed set, a test asserts that none of them groups people, and a breakdown of
anything the public submitted suppresses buckets small enough to describe an
individual.

The **filters** are held to the same line, and this is where it would have
been easiest to miss. "Who verified it?" is a reasonable question and the
platform answers it — on the record's own approval trail, which names the
reviewer, the decision and the time. What it does not offer is that fact
across aggregates: there is no `verified_by`, no `created_by`, no
`assigned_to` among the six filters, because a filter like that turns an
accountability trail into a league table of staff. Tests assert that no filter
names a person and that none ends in `_by`.

Field operations (§18) is where it applies to staff. A mission records where a
team is going and when, because a coordinator has to know where to send help.
It does **not** record a position per person: `mission_check_in` and
`mission_member` have no coordinate column, and tests assert that. A check-in
is a state — safe, delayed, assistance required — not a track. Section 20's
limit on collection is written about citizens; staff did not stop being people
by being employed.

## Known gaps in what is CONFIRMED

Honest caveats about things that do work:

1. **Historical audit entries have no prior value.** Every transition
   endpoint now captures the prior state, so new entries say what a record
   moved *from*. Entries written before that change carry only what the
   record became, and the feed reports them honestly as `had_previous: false`
   — `verification status → verified` with no left-hand side — rather than
   claiming the field had been unset. Nothing backfills them, and nothing
   can: the value was never recorded.
2. **Rate limiting is per-process by default.** `RATE_LIMIT_STORAGE_URI`
   must point at Redis before running more than one worker, or each worker
   enforces its own separate allowance.
3. **Search uses the `english` text configuration for all content**,
   including content in Hausa, Nupe or Pidgin. Stemming will be wrong for
   those languages. Fixing it properly means a per-language configuration
   and a vector per language.
4. **No soft delete.** Deleting a record that was never published removes it.
   Published records cannot be deleted at all — they are withdrawn and
   archived — but the distinction rests on status checks in the API, not on a
   database constraint.
5. **The approval trail is append-only by convention, not by permission.**
   Nothing in the schema prevents a direct database write from altering it.
6. **A withdrawn record can stay on the public portal for up to 60 seconds.**
   The portal revalidates its cached pages on that interval, so a retraction
   is not immediate in the browser even though the API stops serving the
   record at once. Measured, not assumed: after a withdrawal the API returned
   the record as gone immediately and the portal cleared on the next
   revalidation. Withdrawal is the mechanism for taking back something that
   should not be public, so the delay matters. The proper fix is for the API
   to call a revalidation endpoint on the portal when a record is withdrawn,
   which needs a shared secret and an endpoint that does not exist yet.
